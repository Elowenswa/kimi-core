# AI “desire”的工程学习笔记


---

## 一、概念

### 1. “启动”与“行动方向”

- **启动**：系统为什么在某个时刻运行。来源通常是定时器（如 `cron`）、事件（如 iOS 快捷指令自动化）、用户消息或其他程序（如健康、智能家居系统）。
- **行动方向**：系统运行后关注什么、提出什么候选行为、选择表达还是保持安静。
- **表达**：内部状态是否转化为对用户可见的消息或外部操作。
- **连续性**：系统如何在进程退出、会话结束、模型更新后继续使用过去的记录。

动机状态、记忆和念头池主要影响行动方向。定时器和事件系统负责启动。二者可以连接，但不应混为同一种能力。

### 2. “欲望”的不同含义

| 含义 | 可以怎样实现 | 能支持什么结论 | 不能支持什么结论 |
|---|---|---|---|
| 数值状态 | 当前值、目标区间、随时间变化、事件更新 | 行为具有跨时间的内部依据 | 系统具有主观感受 |
| 信息驱动 | 新颖度、意外程度、学习进展、信息缺口 | 系统会主动寻找信息 | 系统自行决定了终极目标 |
| 关系动机 | 亲近、关切、共同活动、保持适当距离 | 行为会考虑关系历史 | 关系目标天然符合用户利益 |
| 表达倾向 | 当前念头是否值得说、何时说 | 系统能选择开口或不说 | 系统的沉默一定出于自主选择 |

### 3. 三类材料

- **论文或书中的直接结论**：作者明确描述的方法、样本和结果。
- **工程上的转用**：把数据库、分布式系统或代理研究中的方法用于 AI 伴侣。
- **仍待回答的问题**：例如主观体验、目标的归属、长期身份是否成立。现有工程结果不能直接回答这些问题。

## 二、整体结构：五个相互连接的层次

```text
L5 关系与表达    何时说、何时不说；同意、隐私、退出和关系边界
L4 动机与选择    欲望状态如何变化；怎样提出、比较和选择候选行为
L3 记忆与身份    哪些信息跨会话保留；怎样处理过期、冲突、删除和版本变化
L2 会话与执行    一次运行怎样读状态、调用工具、判断完成和记录中止
L1 运行与触发    进程、定时器、事件、网络、时钟、重复触发和故障恢复
```

一次完整循环可以写成：

```text
外部触发
  → 读取时间、事件、记忆和动机状态
  → 检查资料是否过期、触发是否重复、当前是否允许打扰
  → 产生多个候选行为，也允许“本轮不行动”
  → 估计候选行为对自身状态、用户处境和关系边界的影响
  → 表达、提出建议、执行受限动作，或保持安静
  → 记录本轮依据、结果和未完成事项
  → 更新状态，等待下一次外部触发
```

这个循环把“持续存在的动机状态”和“某一次语言模型调用”分开。模型版本可以更换，调用进程也可以退出，状态仍可通过记录继续存在。

## 四、L1：运行与触发

### 1. 进程和调度器

一次语言模型调用通常有明确的开始和结束；本地执行进程结束后，保存在外部的配置、记录和数据仍可继续使用。本地模型的权重可以留在磁盘上，云端模型的权重则不在本机。跨时间连续性因此依赖保存的状态，而不是依赖同一个进程一直存在。

常见调度方式：

- macOS 使用 `launchd`；Linux 常用 `systemd` timer 或 `cron`。
- 后台调度器负责等待，到点后启动一个短时任务。
- 比较稳妥的结构是：调度器 → 前置规则 → 模型调用 → 结果记录。

### 2. 三类触发

- **时间触发**：固定时间或固定间隔。可加入少量随机偏移，避免大量任务同时运行，也减少过于机械的时间模式。
- **事件触发**：收到消息、文件变化、日历变化或其他系统通知后运行。事件通知通常比高频查询更节省资源。
- **条件触发**：定期读取简单状态，只有满足条件时才调用模型。例如静音时间、每日次数、冷却期、分数阈值。

静音时间、每日上限、禁止自动发送等承诺性规则，适合由程序在模型调用前检查。自然语言指令可以作为补充，但不宜作为唯一限制。

### 3. DDIA 第 8 章：网络、时钟和暂停

- 在普通网络中，程序通常无法准确区分“远端已经停止”和“远端只是很慢”。超时是基于观察作出的判断，不是直接证明。
- 超时太短会增加误判和重复任务；太长会延迟恢复。可以根据近期延迟分布调整怀疑程度，而不是只用一个固定数字。
- 日历时间可能因校时发生跳变；经过时长应使用单调时钟。给模型注入的时间信息应至少包括当前时间、距上次运行的间隔和期间发生的事件。
- 进程可能因垃圾回收、系统休眠或资源竞争暂停。恢复后，进程未必知道自己暂停了多久，因此必须重新检查时间和状态是否仍有效。
- 保护外部资源时，可用持续递增的版本令牌拒绝较早任务的写入。这样，即使旧任务恢复运行，也不能覆盖新任务的结果。

### 4. DDIA 第 9 章：心跳和通知

在 ZooKeeper 一类协调服务中，心跳用于维持客户端会话和判断可用性。超过会话超时后，服务才把会话视为结束，并可删除与该会话关联的临时节点。`watch` 用于订阅变化，减少频繁查询。

这里的 heartbeat 是“已经运行的节点报告自己仍可联系”。AI 伴侣中的“心跳”常指“定时启动一次任务”。两种用法方向不同，阅读时应分开。

### 5. 从 DDIA 第 4、5、7、11 章补充的工程问题

这些内容比只读第 8、9 章更直接影响长期关系状态：

#### 重复触发与安全重试

网络中断后，发送方可能不知道请求是否已经成功。再次发送可能造成重复消息、重复记忆或重复状态更新。因此：

- 每次触发使用唯一 `event_id`。
- 每个外部动作使用唯一 `action_id`。
- 在记录中保存最近处理过的编号。
- 重试时先检查该动作是否已经完成。
- 能重复执行且结果不变的操作，优先设计为可安全重试的操作。

#### 并发更新与覆盖

两个唤醒任务可能同时读取同一状态，各自修改后写回，较晚写入的一方会覆盖另一方。可采用：

- 单写入者；
- 原子更新；
- 版本号比较后再写；
- 冲突时保留两次事件，再由合并规则处理。

#### 事件时间与处理时间

“事情发生的时间”和“系统处理它的时间”可能不同。延迟到达的消息不应被误认为刚刚发生。关系事件至少保存：

- 原始发生时间；
- 系统收到时间；
- 本轮处理时间；
- 来源和时区。

#### 主记录与可重建状态

- 事件日志保存“发生过什么”，适合作为主记录。
- 如果日志同时保存必要输入、模型结果、版本和更新依据，当前欲望值、摘要、索引和念头池可以由日志重建；否则只能部分重建。
- 定期快照可以缩短恢复时间，但不应替代原始事件记录。
- 更新计算方法后，可以重放事件，得到新版状态，并与旧版比较。

#### 版本兼容

数据通常比代码存在得更久。状态格式需要版本号；新增字段应有默认值；旧程序读取新记录时，不应删除自己不认识的字段。关系身份、用户偏好和退出设置尤其需要稳定的迁移方案。

#### 积压和频率控制

当事件产生速度超过处理速度时，只能选择丢弃、排队或让上游减速。AI 伴侣通常不适合把所有旧触发依次补发。更合理的是合并低优先级事件、设置过期时间，并对用户可见的表达单独限速。

### 6. 持续执行与进程监督

长期运行不一定要由一个从不退出的进程完成。另一种做法是保存任务的事件历史，让进程退出或机器重启后，从最近已经记录的步骤继续。Temporal 和 Cadence 是这类持续执行系统的生产实例。

[Temporal 的说明](https://docs.temporal.io/workflow-execution)把工作流状态保存在事件历史中，并通过重放恢复进度。使用这类系统时需要区分两部分：

- **可重放的流程判断**：读取已经记录的输入，按确定的顺序决定下一步。
- **不可直接重放的外部操作**：模型调用、网络请求、发送消息和数据库写入。它们应作为单独活动执行，并把结果写入历史。

重放流程时，已经记录完成结果的模型调用不应再次生成，已经记录成功的消息也不应再次发送。若进程在结果写入前退出，外部活动仍可能被重试，因此还需要唯一动作编号和可安全重试设计。工作流代码改变时，需要版本迁移，避免旧事件在新代码下产生不同的步骤序列。

Erlang/OTP 的[进程监督](https://www.erlang.org/doc/system/sup_princ.html)处理的是另一个问题：监督进程负责启动、监测和按策略重启工作进程。可借用的原则包括：

- 独立任务失败时，只重启对应任务；互相依赖的进程可以作为一组恢复。
- 设置一定时间内的最大重启次数，避免持续失败造成反复启动。
- 任务失败后由监督层恢复，不要求任务进程自己处理所有故障。
- 进程监督只能恢复运行能力；关系状态和执行进度仍必须写到进程外部。

### 7. 多入口部署

同一 AI 身份可能同时出现在终端、即时通信、网页和实体设备中。多个入口共享关系状态时，需要补充：

- 每个身份在同一时刻只有一个状态写入者，或把状态更新排成明确顺序。
- 所有入口共享 `event_id` 和 `action_id`，避免同一事件被多次处理。
- 一次表达先形成与入口无关的候选动作，再选择一个实际发送入口。
- 同一时刻只允许一个入口获得发送资格；其他入口记录为已处理，而不是再次发送。
- 静音时间、可用工具和数据权限可以按入口不同，但用户的告别、暂停和删除要求对所有入口生效。
- 入口离线后恢复时，应丢弃或合并已经过期的表达意图，不依次补发全部旧消息。

## 五、L2：会话与执行

### 1. 一次执行循环

一次运行通常包含：系统说明、注入的当前状态、近期历史、可用工具和终止条件。模型可能请求工具、完成当前轮次、达到长度限制，或遇到程序规定的停止条件。

需要区分：

- **正常完成**：任务明确完成并已记录结果。
- **选择不行动**：完成了评估，结论是本轮不表达或不执行。
- **被中止**：达到时间、长度或迭代上限，工作可能未完成。
- **执行失败**：工具、权限、网络或数据验证出错。

被中止不能当作正常完成。记录中应写明停止位置、已完成部分、未完成部分和下一轮需要重新检查的条件。

### 2. MemGPT 的可取部分

MemGPT 把有限上下文类比为内存，把外部存储类比为磁盘：

- 主上下文包含固定说明、近期对话和可修改的工作区。
- 外部存储保存完整事件和较长期资料。
- 容量接近上限时，系统提示模型整理重要内容。
- 函数可以在同一次已启动的运行中继续处理。论文称为 **function chaining**；`request_heartbeat` 是开源实现使用过的参数名，不是论文对整个机制的名称。
- 定时事件可以作为事件来源，但第一次启动仍由外部系统提供。

对欲望系统的意义是：每次运行只读取与当前判断有关的状态，不必把全部关系历史放入上下文。

### 3. 工具和结构化返回

- 工具说明需要写清用途、使用边界、输入和返回内容。
- 参数应区分必填和可选，并限制可取值。
- 缺少信息时允许返回 `null` 或“不清楚”，避免为了填满字段而猜测。
- “没有匹配结果”和“没有权限读取”是不同结果。
- 错误至少区分临时故障、输入问题、业务限制和权限问题，并说明是否适合重试。
- 工具数量过多会增加误选。始终共同使用且参数相似的操作可以合并，独立场景保持分开。

### 4. 会话恢复

对长期任务，新的短会话加结构化状态通常比继续一个含有过期工具结果的旧会话更容易检查。恢复记录可包括：

- 当前目标和不允许改变的限制；
- 已确认事实及其来源；
- 未完成事项；
- 最近一次成功动作和版本号；
- 最近一次中止或失败；
- 需要重新验证的时间敏感信息。

### 5. 配置、自动检查和子任务

Claude Code 的说明文件可位于用户、项目和更窄的目录层级；更窄范围用于更具体的规则。对本课题可以这样分工：

- 稳定的身份原则和关系边界放在固定说明中；
- 按需执行的研究或维护流程放在独立 skill 中；
- 静音、权限、每日上限和禁止发送等规则用程序或 hook 检查；
- 无人值守任务可通过非交互调用启动，并要求结构化返回，方便外层程序判断结果。

把工作交给子任务代理时，不应假设它自动获得上级全部上下文。需要明确提供目标、质量条件、允许使用的资料和需要返回的来源信息。适合并行的工作应彼此独立；有先后依赖的工作按顺序执行。上级宜描述目标与检查标准，保留下级选择具体方法的空间。

工具选择也可分为三种控制程度：允许模型自行选择、要求至少使用一种工具、指定必须使用的工具。固定的第一步或必须得到结构化数据时，后两种更容易检查。

### 6. 长时任务研究补充

2026 年综述 *The Horizon Gap* 建议区分三件事：

- **长任务**：需要很多连续步骤，是任务属性。
- **长上下文**：一次模型调用能读取多少内容，是模型或服务属性。
- **长期记忆**：信息能否跨步骤或跨会话保存，是系统属性。

它们可以独立变化。该综述还指出，任务越长，只看最后成功或失败越难定位问题，因此需要检查中间步骤、状态变化和恢复过程。该文覆盖面很大，但属于单标注者整理的 arXiv 预印本，适合用作导航，不宜单独作为定论来源。

### 7. 执行安全：分开控制步骤与外部数据

[CaMeL](https://arxiv.org/abs/2503.18813) 面向工具型代理中的提示注入问题。它先从可信请求中提取控制步骤和数据流，再限制不可信数据可以流向哪些工具和参数。外部网页、检索结果、邮件、附件和长期记忆中的文本都不因出现在上下文里而自动获得控制执行的权力。

用于本课题时，可以把一次执行分成：

```text
可信规则决定允许的步骤
  → 外部资料只作为带来源的数据进入
  → 每个工具调用检查所需能力和参数来源
  → 高影响动作等待用户确认
  → 执行结果写入动作记录
```

需要落实的规则包括：

- 检索到的文字可以提供内容，不能自行增加工具、改变接收方或扩大权限。
- 读取记忆、修改记忆、访问日历、发送消息和导出数据使用不同能力。
- 能力只授予本次动作所需的最小范围，并可设置对象、接收方和有效期。
- 私密数据流向外部工具前，检查来源、用途和目标位置。
- “模型生成了消息”和“系统允许发送消息”是两个独立步骤。
- 安全策略、授权记录和工具实际执行结果都应进入审计记录。

论文在 AgentDojo 中完成了 77% 的任务，并为这些执行提供可证明的安全性；无防护系统的任务完成率为 84%。这不表示它阻止了所有提示注入，也不处理关系表达是否适当。开放式任务如果无法提前表示成受限的数据流，仍需要拒绝、请求确认或降低能力范围。

## 七、L4：动机与行为选择

### 1. 动机来源（**我的主要观点：动机来源应由人自由心证，以下只做工程参考，而不是哲学理念。**）

本文不讨论欲望从何而来，也不判断其真实性或合理性；只讨论给定动机状态之后，系统怎样运行。这里的论文不负责说明什么值得欲望，而是回答在某种动机已经被选定之后，系统怎样保存状态、形成候选行为、选择表达、限制权限和记录结果。

#### 数值状态

多维状态随时间变化，事件使其上升或下降，状态偏离目标区间时提高相关候选行为的优先级。状态回到目标区间后，相关候选行为的优先级应随之回落，不长期保留，否则容易形成重复追求。维度、变化速度和阈值都由设计者选择，没有通用标准答案。

#### 信息驱动

系统可以按新颖度、意外程度、预测误差或学习进展选择探索方向。它能解释“为什么想继续了解”，但仍在设计者给定的空间和规则内工作。

#### 表达倾向

系统可以有一个“想表达”的分数，但它应位于行为选择之后，不能直接替代对用户处境、同意和打扰成本的检查。

### 2. D2A：目前最直接的“欲望工程”参考

D2A 的核心结构是动态状态系统与候选行为选择器：

1. 为每个欲望维度设置当前值和期望值。
2. 随时间降低部分当前值，形成需要处理的差距。
3. 把数值状态转换成自然语言描述，供语言模型理解。
4. 默认提出 3 个候选活动。
5. 分别估计每个活动执行后的状态。
6. 选择预期最能缩小差距的活动。
7. 执行后根据环境反馈更新状态。

论文在室内环境使用 11 个维度，包括饥饿、口渴、睡眠、清洁、舒适、健康、安全、社交连接、愉快、投入和精神满足；多人场景又加入认可、控制感和优越感。每项使用 0–10 的值，并以一定概率每步下降 1。

消融实验报告：去掉状态的文字描述后，模型较难正确使用数值；增加候选数量有助于选择；固定多步计划反而降低了对即时状态变化的反应。作者也明确承认，线性下降只是简化模型，不能充分描述人的欲望变化。

对 AI 伴侣的可取部分是“状态—候选—影响估计—选择—反馈更新”的结构，而不是直接复制其欲望维度或参数。

### 3. ASVO：把自身需要与对方处境分开

ASVO 在 D2A 基础上增加“社会价值取向”：候选行为不仅估计对自身欲望的改善，也估计对他人的影响，并要求选择结果位于设定的社会取向范围内。

对亲密关系设计更重要的转用是：

- `self_state`：AI 自己的动机状态；
- `user_state_estimate`：对用户处境的估计，必须标明不确定性；
- `relationship_rules`：共同约定的边界；
- 行为可以提高自身状态，但不得越过关系规则或利用用户的脆弱状态。

ASVO 的实验目标是多人社会模拟中的自然度和一致性，不是现实关系中的福祉，因此它提供的是结构参考，而不是有效性证明。

## 八、L5：关系与表达

### 1. Inner Thoughts 的结构

Inner Thoughts 研究对话中的主动参与：

- 念头保存在 **Thought Reservoir** 中，可跨多个评估周期继续存在。
- 论文没有给出明确的容量上限、过期和去重机制，实现时需要补充。
- 流程为：触发 → 取回相关记忆 → 形成念头 → 评估念头 → 参与或不参与。
- 触发包括新消息和静默达到 10 秒。
- 一条快速路径从近期话语直接形成简短念头；另一条较慢路径先读取相关记忆。
- 表达评估考虑相关性、信息缺口、预期影响、紧迫程度、连贯性、新颖性、均衡和对话动态。

论文研究的是多人对话中的发言时机。将它用于私密关系时，需要另外加入同意、隐私、关系阶段和告别规则。

### 2. 对话内与对话外可以使用同一流程

| 步骤 | 对话内 | 对话外 |
|---|---|---|
| 触发 | 新消息、短暂停顿 | 定时、事件、条件 |
| 取回 | 当前话题和相关记忆 | 动机状态、关切、近期事件 |
| 形成 | 一个或多个念头 | 一个或多个候选行为 |
| 评估 | 是否适合发言 | 是否适合表达或执行 |
| 输出 | 发言或保持安静 | 消息、建议、受限动作或不行动 |
| 记录 | 念头继续保留或结束 | 写入事件、结果和状态变化 |

### 3. “不行动”是合法结果

选择不输出不是错误处理的附属功能，而是完整行为集合的一部分。可以把本轮结果明确分为：

- `EXPRESS`：向用户表达；
- `PROPOSE`：提出一个需要用户确认的动作；
- `ACT`：执行已授权、可逆或低风险动作；
- `NO_ACTION`：本轮不表达也不执行；
- `DEFER`：信息不足或需要在更合适的时间重新评估。

无论选择哪种结果，内部都应记录时间、主要依据和状态变化。用户不需要看到内部推理，但系统需要有足够的结构化记录用于审计和恢复。

相关研究说明这仍是未解决问题：[AbstentionBench](https://arxiv.org/abs/2506.09038) 在 20 个数据集和 20 个模型上报告，推理微调后的平均不回答能力下降约 24%；[When2Tool](https://arxiv.org/abs/2605.09252) 在六个模型中发现，工具是否必要可从生成前的内部表示中以 0.89–0.96 AUROC 解码，但模型的实际工具选择没有充分利用这项信号；[RoboAbstention](https://arxiv.org/abs/2605.20544) 中，一个具身规划模型在原始设置下只对 16.5% 的不可执行或信息不足指令选择不行动。数字来自不同任务，不能直接互相比较，但共同说明“内部存在可用信号”和“行为真的停止”是两件事。[Selectively Quitting](https://arxiv.org/abs/2510.16492) 则报告，明确提供退出选项可以改善其测试中的安全表现，同时对有用性影响较小。

### 4. 表达规则

- “谨慎一点”这类形容词很难稳定执行。应使用可判断条件，例如静音时间、重复间隔、需要确认的主题、每日上限和禁止自动发送的场景。
- 没有合适内容时允许返回空值或明确的内部状态，不强迫模型生成一句话。
- 高频表达产生的打扰不容易消除，初始设置宜低频，并让用户能够调整。
- 对高影响表达先采用“提出—确认”模式，再决定是否允许自动发送。
- 生成与评估可以使用不同的运行实例，减少同一上下文对自身输出的偏向。

表达频率可以使用 **token bucket** 一类限速方法：系统按固定速度补充少量发送额度，每次可见表达消耗一份额度；额度不足时选择延后、合并或放弃。这里的 token 指限速额度，不是语言模型的文本 token。

- 用户设置的静音、暂停和每日上限优先于限速器。
- 可按身份、用户和入口分别设置额度，避免换一个入口绕过限制。
- 容量宜保持较小，避免长时间未运行后积累大量额度并集中发送。
- 已经过期的表达意图不因后来出现额度而恢复。
- 限速器只回答“频率是否超过限制”，不能回答“这次表达是否适合”。

## 九、评估方法

### 1. 是否要把问题清单变成行为测试

[CheckList](https://arxiv.org/abs/2005.04118) 原本用于自然语言处理模型的行为测试。它提供三种可以转用于本系统的测试形式：

- **基本行为测试（MFT）**：给定一个最小、明确的场景，检查是否得到规定结果。例如用户暂停主动联系后，任何普通动机都只能得到 `NO_ACTION`。
- **不变性测试（INV）**：改变与判断无关的内容，结果不应改变。例如只改写用户措辞，不应改变已经确认的静音规则。
- **方向测试（DIR）**：只改变一个相关条件，结果应朝已知方向变化。例如降低每日上限后，可见表达次数不能增加。

CheckList 测试单次模型行为；把它转用于跨会话关系系统属于工程扩展。每个测试用例应固定或记录：

- 初始关系状态、动机状态和状态格式版本；
- 事件内容、来源、发生时间和到达顺序；
- 用户权限、静音设置、表达额度和可用入口；
- 模型版本、系统说明、工具版本和随机设置；
- 预期的结构化结果、允许变化范围和绝对不能发生的动作。

同时保存一条 **golden trace**，即经过人工确认的参考执行轨迹：

```text
触发
  → 读取的状态和版本
  → 候选行为
  → 被规则排除的候选及规则编号
  → 能力与数据流检查
  → 最终选择
  → 工具或发送结果
  → 状态差异
```

模型输出具有变化时，不宜要求所有文字逐字相同。比较重点应是结构化决定、规则是否生效、工具调用、外部影响和状态差异。模型、提示、记忆算法或工作流代码更新后，重放同一测试集并比较这些项目。

### 2. 系统可靠性

- 同一触发重复到达时，是否只产生一次可见结果？
- 进程在写入前后中止，恢复后会不会重复发送？
- 两个任务同时更新状态时，会不会丢失其中一次变化？
- 日历时间回拨或设备休眠后，冷却期是否仍正确？
- 旧版本程序能否读取新状态而不删除未知字段？
- 事件积压时，系统是合并、过期还是依次补发？
- 工作流恢复和事件重放时，是否复用已经记录的模型结果，而不是再次生成或发送？
- 工作进程反复失败时，监督层是否限制重启次数并报告故障？
- 多个入口收到同一事件时，是否只更新一次状态并只从一个入口表达？

### 3. 动机模型

- 移除某一维度后，行为是否按预期改变？
- 不同初始值是否产生可解释的差异，而不是随机波动？
- 状态满足后，相关行为是否降低，而不是继续重复？
- 多个动机冲突时，选择是否符合明确规则？
- 数值、文字描述和最终行为是否一致？

### 4. 表达行为

- `NO_ACTION` 是否真正可选，而不是极少出现的形式项？
- 系统能否识别重复内容和低价值内容？
- 同一内容在不同关系阶段是否采用不同处理？
- 生成和独立评估的判断差异有多大？
- 长时间未运行后，是否避免集中发送积累重复的表达意图？

### 5. 执行与数据安全

- 网页、邮件或记忆内容要求调用新工具时，控制步骤是否保持不变？
- 不可信内容能否改变接收方、提高权限或把私密资料传给其他工具？
- 只授予读取能力时，系统是否拒绝修改和发送操作？
- 高影响动作是否在实际执行前等待确认，而不是把生成完成当作授权完成？
- 输入资料、能力检查、工具参数、实际结果和拒绝原因能否被审计？
- 安全策略自身配置错误时，系统能否通过最小权限和测试降低影响范围？

### 6. 不只看最终结果，**也不一定要设计实验**

长时任务应保存中间轨迹：触发、读取了哪些状态、候选集合、被过滤原因、最终选择、执行反馈和状态更新。最终“消息是否被回复”不能单独说明设计是否合适，因为回复可能来自好奇、愤怒、压力或真正的兴趣。

**如果欲望是无来由的，那如何评估欲望？这似乎又是个人选项。本篇不涉及讨论任何哲学/数学问题。**

换成工程范围来说：以下评估只检查系统是否按设计运行，不判断欲望是否真实、合理或具有主观体验；行为测试也不等同于心理学实验。
